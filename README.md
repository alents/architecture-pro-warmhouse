### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах в веб-интерфейсе Системы.
- Система управляет отоплением, отправляя команды включения/выключения на специальные модули, установленные в домах. 
- Система поддерживает только определенные датчики/модули управления отоплением
- К Системе подключено 100 клиентов и модулей управления отоплением

**Мониторинг температуры:**
- Система получает данные о температуре с датчиков, установленных в домах.
- Система поддерживает только синхронные запросы к датчикам
- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс Системы.

### 2. Анализ архитектуры монолитного приложения

Архитектура веб-приложения представляет из себя монолит на языке Go с СУБД Postgres. Система взаимодействует с датчиками получения текущей температуры
и управляющими модулями, включающими и выключающими отопление, отправляя им синхронные запросы.

### 3. Определение доменов и границы контекстов

Сделаем допущение, что датчик это единая точка управления отоплением. То есть у датчика приложение запрашивает температуру
и отправляет датчику команды управления отоплением. Каким образом реализовано взаимодействие датчика с системой отопления в
доме, в рамках разрабатываемой архитектуры мы не рассматриваем. 

| Субдомен                                                  | Bounded Context             | Решаемые задачи                                                                                                 |
| --------------------------------------------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Получение температуры                                     | Monitoring Context          | Получение и хранение данных о температуре с датчиков (для UI и управления)                                      |
| Публикация температуры                                    | часть Monitoring Context    | Отображение значений датчиков в UI                                                                              |
| Включение/выключение отопления                            | Heating Control Context     | Управление отоплением, сценарии включения выключения                                                            |
| Работа с клиентами                                        | Customer Management Context | Регистрация пользователей, профили, привязка датчиков к клиенту                                                 |
| **Интеграция с датчиками** _(техническая инфраструктура)_ | Device Integration Context  | Работа с физическими устройствами: регистрация устройств, протоколы, сетевые адреса, запросы/команды к датчикам |


### **4. Проблемы монолитного решения**

- При увеличении количества датчиков функционал получения телеметрии может стать узким местом, но отдельно
его масштабировать не получится.
- По мере добавления новой функциональности и появления новых поддерживаемых типов устройств монолит будет сильно усложняться. 
Это увеличит время доставки новых фич и ухудшит надежность системы. 
- При сбое монолита вся система станет недоступной для пользователей.
- При обновлении требуется остановка всей системы

С другой стороны, данное приложение не требует сложной инфраструктуры и дополнительных компетенций 
для развертывания и эксплуатации.

# Задание 4. Создание и документирование API

### 1. Тип API

В своем решении я буду использовать синхронное REST API для взаимодействия в тех случаях, когда ответ может быть получен 
относительно быстро (без продолжительных вычислений, без ожидания завершения какого-либо процесса, который может занимать 
продолжительное время). Асинхронное взаимодействие (через брокера) я буду использовать для случаев, когда не нужен
ответ на запрос либо допускается получить ответ позже.  
Например, между монолитом WebApp и микросервисом DeviceManager предполагается синхронное взаимодействие, так как функционал сервиса
связан с регистрацией устройств в базе данных и трансляцией запросов статуса и команд на сами устройства. Сервису WebApp
результат этих действий нужен сразу, а не когда-то в будущем.  
С другой стороны, между микросервисами SensorPoller и TelemetryCollector асинхронное взаимодействие, так как SensorPoller опрашивает
датчики и публикует события о том, что доступны новые значения датчиков, а TelemetryCollector получает данные события и 
сохраняет телеметрию в БД. На данные события могут быть подписаны также другие микросервисы. Такое решение позволяет 
легко масштабировать микросервис SensorPoller в случае роста количества опрашиваемых датчиков, а так же переиспользовать его
в разных сценариях, так как он выполняет всего одну бизнес-функцию (опрос датчиков) и не занимается какой-либо обработкой,
сохранением полученных данных (что потребовало бы зависимости от определенной СУБД).

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры
